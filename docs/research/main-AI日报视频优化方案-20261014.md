## 1. 结论与优先级

**优先把“长标题速读＋密集图文卡”改成“能看懂的开发者新闻速览”，同时让不合格产物无法自动发布。** 现有 edge 云希配音、KTV 字幕、1080×1920 画布、Remotion 4.0.520、日期输出目录与外部发布工具都能继续复用。

当前主要矛盾有三层：

1. **观众得到的信息不匹配观看时间**。10-14 每条新闻约 5—6 秒，但画面正文合计 1,901 字符，口播主要只念标题；观众需要同时听长标题、读密集细节和看关联较弱的图片。前约 4 秒主要在展示日期与“7 条精选”。
2. **自动验收的覆盖面不够**。文字/品牌卡漏检、语音失败静音只告警、图片路径失效只告警、混音失败仍归档、片尾空背景没有检查，都可能继续流向发布。
3. **提示词承担了程序应承担的工作**。清除当日去重记录、控制标题超过 32 字、音频临时修补、手工回写章节、强制重绘封面等操作持续堆进提示词；入口文档又与真实代码不一致。

建议按以下顺序推进：

| 优先级 | 首要变化 | 直接收益 |
|---|---|---|
| P0 | 统一文档与命令、完整产物报告、关键质量门、重跑不污染状态 | 防止错误发布与反复人工救火 |
| P1 | 缩短开场、减少正文、分离显示/朗读文本、改善选图、消除空尾 | 提升可读性与信息传达质量 |
| P2 | 可追溯素材快照、受控重试、平台发布账本、留存实验 | 提升自动化稳定性，检验真实运营收益 |

不建议优先换 TTS、全量启用 Whisper、升级 Remotion 或迁移视频框架。当前证据没有显示这些是主要瓶颈。旧方案中的章节、发布物料、run report 等能力已经有实现，重点是修正可信度与归档完整性，避免重新开发一套。

## 3. 可借鉴的成熟做法与适用边界

外部依据集中在第 7 节。本项目采用其机制，优先复用现有工具：

| 维度 | 成熟做法 | 当前差距 | 适配方案 |
|---|---|---|---|
| 数据驱动渲染 | Remotion 提供基于输入的数据契约、渲染元信息与 schema 机制 [1][3] | 配置表面可传文件，前端却读固定共享文件；大量 `any` | Python 执行完整输入校验，前端补少量明确类型；需要时用 props/metadata 连接同一快照 |
| 渲染资源 | Remotion 允许控制并发，按资源实测调节 [1][2] | 固定并发 2，OOM 后重试仍用相同参数 | 本机先设 1，保存耗时/峰值内存；仅对已识别瞬态失败做一次受控重试 |
| 音频后期 | FFmpeg 分别测量综合响度/真峰值并支持侧链压缩 [4] | 历史将峰值/RMS 当成响度达标；能力探测与实际滤镜链不一致 | 真实微型链路预检，成片后引用输入测量；音轨测量与人耳听审并存 |
| 幂等任务 | 固定输入、重跑同一工作单元得到一致结果 [5] | parse 写去重账本，fetch 清共享图片，缓存按句序复用 | 日期/run 快照＋内容指纹＋完成后提交状态；无需引入 Airflow 服务 |
| 移动端可读性 | 核心内容避开平台 UI，按真实尺寸检查；官方广告指南提示安全区会变化 [6] | 固定区域、长段正文、实际字幕可能三行 | 用项目安全区草案和三平台模拟遮罩验证；平台广告指南仅供参考，不直接当自然视频统一规范 |
| 运行可观测性 | 记录真实输入、阶段结果、产物哈希和失败原因 | 报告常量填充，返工后缺报告 | 扩充现有 JSON，不搭指标平台；保留逐阶段结构化结果与本机日志 |

已有 Remotion 4.0.520 满足本次所需基础能力。没有理由为方案新增渲染引擎、付费配音、重型工作流调度器或大模型视觉服务。若后续引入新库，须另核许可证、Windows 支持、缓存路径和成本；复用 Remotion 不等于其商业许可条件发生改变。

## 4. 推荐的成片与内容方案

### 4.1 保持栏目定位，改变信息组织

继续面向 Java/Python、AI Coding、Agent/RAG 与本地部署开发者；正文摘要仍保持 6—7 条、AIHOT 双入口、原文链接和完整的“核心/细节/价值”。**完整新闻简报和视频口播是两个编辑产物**，二者共享事实，但不要求显示、朗读、长文三个字符串完全相同。

建议每条视频只交代一个主要事件与一个开发者影响，数据、适用限制、来源在有限位置补充。默认先做七条 50—60 秒版本，不擅自把栏目缩为三条。若某天确实不足六条有据高价值新闻，应明确记录不足并按编辑策略处理，不能为凑条数或时长拿过期低质量条目填满。

建议结构（初始预算，最终以合成后的真实时长回算）：

| 段落 | 时间预算 | 内容 |
|---|---:|---|
| 开场 | 0—2.5 秒 | 当天头条的具体变化；日期与栏目角标不单独占四秒 |
| 头条 | 约 7.5 秒 | 发生了什么＋对开发者有什么用 |
| 其余六条 | 每条约 6.5—7 秒 | 每条一个主要变化或结果，避免长专名堆叠 |
| 收尾 | 约 1.5—2 秒 | 一个具体讨论问题或“明天见”；最后画面继续覆盖缓冲 |

开场信息与头条避免重复朗读。头条已在开场完成的“主体＋动作”可以从后续头条句中省去，不能为了时长再次复读。总时长超过 60 秒时改写信息密度最低的句子；低于 50 秒时补有来源支持的影响或限制，禁止靠加速/放慢、长停顿或纯背景凑数。

以当前输入第 3 条为例，可以把画面改为“**20 万行 Python，Agent 通宵优化**”，只展示“6 项提案，2 项合并”和“导入耗时下降 21%”等少量信息；口播为“Google 用 Argon 通宵优化 ADK，六项提案合并两项，包导入耗时下降百分之二十一。”这只是从当前新闻稿提炼的样稿，**数字与事实尚须对照原文核验，不能直接当作已核验新闻发布**。

### 4.2 显示稿与朗读稿共享语义，分开转换

最小改动应扩展现有 narration，而不是立刻创建复杂 CMS：

```text
source_title / source_url / published_at / fetched_at / aihot_item_id
    ↓ 编辑，保留证据引用
display_title / display_points / chapter_title / spoken_text
    ↓ 仅在 TTS 边界做术语读法转换，记录映射
spoken_text_normalized → 音频 + words/chars → 字幕显示映射
```

- `display_title` 保持 GPT-5.6、AWS、RAG 等原始写法，不出现“G P T 五.6”。
- `spoken_text` 必须是完整句，初次合成前可导出审阅稿；脚本导出与人工批准是两种不同模式，无人值守不增加隐含等待步骤。
- 配图补充阶段只更新素材，不覆盖已冻结的 `spoken_text`。
- 字幕若显示原始专名，需把归一化发音 token 对齐回显示片段；这比直接把字幕字符串替换掉更可靠。先支持实际常见术语，其余保留可验证的现有形式，不能虚构精确对齐。
- 章节使用显式 `chapter_title`，如“Argon 模型上线”“Scion 版本管理”，保留词义，不做 `title[:20]`。
- 先补事实依据：条目日期、AIHOT ID/条目页、原文 URL、摘要抓取时间；“作者称/官方报告/第三方实测”等归因必须留在稿件中，不能压缩成无条件结论。

### 4.3 版式：减少正文后再加大字体

建议基于现有深蓝、青蓝/黄色、codebase-style 品牌做收敛，首期不用换视觉系统。1080×1920 初始布局：

| 区域 | 建议位置/约束 | 验证方式 |
|---|---|---|
| 栏目与序号 | y≈140—230，弱化分类胶囊 | 所有必要信息在平台模拟遮罩内可见 |
| 主标题 | y≈270—470，最多两行，约 56—68 px | 真实字体与最长专名边界测量，长标题应改写 |
| 事件照片 | y≈520—1050，保留主体完整 | 延续 contain 原则，不通过 cover 强裁主体；示意照片明确标注 |
| 关键结果 | y≈1110—1280，至多两条、合计约 40—50 中文字符 | 约 36—42 px，屏幕实测最多四行，不能直接搬 300 字细节 |
| 来源 | 单行可信来源名/域名，小而清晰 | 七条均非空，URL 细节放简介 |
| KTV 字幕 | 独立区域，底边约 y=1510—1560；最多两行 | 与正文边界至少留 40 px，按像素宽度分页；360px 手机宽预览 |
| 平台覆盖预留 | 初始保守留出底部约 320px、右侧约 150px | 三平台不同 UI 遮罩复验后调整；不是平台保证的统一安全区 |

需同时满足“图片主体完整”与“内容布局不越界”。不能只是把正文往下推、把字幕再往下移，或缩字到肉眼难读。固定数量/字号只是起点，最终验收真实换行与区域碰撞。10-12 的三行字幕要纳入固定回归样本。

收尾保留画面，最后场景结束时间应到 Composition 尾部；音频、字幕、场景统一一个 offset。用有明确发声起点的 fixture 验证 0.1 秒风险，字幕主观听审另外执行。

### 4.4 配图：在硬约束内提高匹配度

维持“真实实拍照片、禁止文字卡/海报卡/满屏文字截图”的已定版要求。真实产品摄影可以包含可辨认实物及少量屏幕文字，但不能把品牌数字渲染图算实拍。

建议候选排序：事件本身或设备实拍 → 能说明使用场景的实拍 → 明确标注“场景示意”的相关图库照片；不以“来自原文”直接判定合格。与报道无关的作者头像、站点通用头像、宣传标题卡排除。不要为了“7 张不同”而选择七张完全不解释事件的人像。

首期复用像素判据＋候选页面上下文＋人工/现有多模态抽检，不引入新付费服务。把此次数字 4 卡、品牌横幅、人像弱相关图加入质量样本；基于实际误判调整判据，不能只抬一个阈值误杀正常照片。哈希去重继续保留，近期图片相似度可用已有 Pillow 实现轻量感知指纹；感知哈希只能发现画面相近，不能判断语义相关性。

所有素材记录来源页、下载 URL、下载时间、使用类型与授权依据。新闻原文配图不自动代表拥有再利用许可；图库“免费”也不代表无使用条件。无足够可用照片时阻断正式发布，不能回落海报卡。

### 4.5 音频：先保证可测量与无静音失败

- 固定 edge + 云希男声与 +30% 语速，保持已确认偏好；不启动 GPT-SoVITS。
- 当前原片约 -17 至 -18 LUFS，属于与代码目标不一致，不应据此断言观众一定听不清。
- 项目内部初始目标建议：综合响度 -14±1 LUFS、真峰值≤-1 dBTP；每个版本重新测量 AAC 成片，配合手机外放听审。这个范围不是三平台统一硬性要求。
- 现有备用混音是 RMS 包络＋峰值处理，不等于 EBU R128 综合响度归一化。当前 bundled FFmpeg 的 `-af loudnorm` 可以工作，**缺少的是侧链混音所需的部分能力**；应检测 `asplit/aloop/sidechaincompress/amix/loudnorm` 的实际组合，不沿用“缺 loudnorm”的旧结论。
- 若完整链路可用，统一使用经预检的 FFmpeg；若暂时沿用现有 NumPy 闪避实现，将其正式纳管、再用可用 loudnorm 做后处理与最终测量。两条路不并行长期维护。
- BGM 有无、文件、授权、闪避策略、混音是否成功都写入报告。TTS 失败与混音失败不能伪装成完成：前者阻断；后者按已声明策略阻断或降为明确的“纯人声版”，不能静默发布。

## 5. 提示词与流水线职责调整

### 5.1 推荐链路

```text
定时触发
  → 只读获取 AIHOT A/B 原始响应并保存日期快照
  → 选择 6—7 条、校验时间窗口/原文/归因，生成新闻长文
  → 编辑视频显示稿与完整口播稿，冻结内容指纹
  → 配图候选与质量门 → TTS/时间轴质量门
  → Remotion 渲染 → 混音 → 对最终 MP4 实测和抽检
  → manifest + run_report + 发布文案 + 封面检查
  → 同一成片版本的 READY 门
  → 外部 video-upload 按平台回执发布
  → 合并平台结果、更新当日交接
```

先复用当前 `work/`，增加 run 指纹、一致性检查和互斥锁；再逐步把输入、图片、时间轴、音频快照放到 `work/<date>/<run_id>/`。Remotion 仍需把一次运行明确绑定到正确输入：可以最小化地受控同步到 public 并核对指纹，后续再用 props。仅改目录而前端仍静态 import 旧 timeline，会扩大问题。

### 5.2 配置与结果契约

不让提示词到处拼接路径。配置只保留不含密钥的项目路径、时区、输出策略、后端、语速、并发等；密钥继续从现有 `.env`/环境加载，不写入 JSON、交接和日志。

最终结果应在现有 `run_report.json` 上扩充，而不是另搭服务：

```json
{
  "date": "2026-10-14",
  "run_id": "<日期及输入指纹>",
  "content_sha256": "<实际值>",
  "status": "READY|BLOCKED|GENERATED",
  "video": {
    "path": "<PROJECT_ROOT>/out/2026-10-14/<主视频>.mp4",
    "sha256": "<最终混音后的实际值>",
    "duration_sec": 0,
    "width": 1080,
    "height": 1920,
    "fps": 30
  },
  "quality": {
    "tts_failed": [],
    "images_missing": [],
    "images_reviewed": false,
    "audio_mix_status": "not_checked",
    "integrated_lufs": null,
    "true_peak_dbtp": null,
    "tail_frame_checked": false
  },
  "artifacts": {},
  "publish": {}
}
```

上面是建议 schema 示意，0/null/false 为未测状态，不可直接当成功数据。`READY` 必须由完整校验生成，不能由字段是否存在判断。`GENERATED` 表示文件存在但未完成发布前验收；`BLOCKED` 保存失败阶段和恢复方式。发布器必须核对同一 SHA256 的 READY 结果，避免混音/返工后沿用旧通行证。

至少归档新闻源快照、稿件、narration、timeline、最终 MP4、实际采用的封面、章节、publish.md、质量报告和素材来源清单；原始逐句音频/图片是否长期保留按本机空间制定保留期，运行中及待补发版本不可删除。

### 5.3 提示词候选稿（实施后替换，当前不可照抄执行）

以下可替换冗长的故障记忆，但依赖预检、READY、run 隔离等改造落地。**本次未修改原提示词或正在运行的定时任务，也未验证保存的提示词与调度器实际 prompt 完全一致。**

> 你负责每天生成面向技术开发者的 AI 新闻简报和 9:16 速览视频。业务日期与所有窗口使用 Asia/Shanghai。
>
> 1. 按 todayaihot 当前技能文档进行环境预检，缺少必要能力则保存失败报告。使用同一已验证解释器与渲染运行时，不临时安装全局依赖，不启动 GPT-SoVITS。
> 2. AIHOT 精选接口与全部动态 RSS 配合取候选；latest 404 按索引返回的真实日期请求，不猜日期。不用训练记忆补新闻，不用其他来源冒充 AIHOT。保存来源日期、条目 ID、原文、抓取时间与原始响应；旧精选按实际日期标注，不能当作今日发布。
> 3. 按 AI Coding、Agent/RAG、Java/Python 与本地部署相关性选 6—7 条，跨日排重但允许同一输入安全重跑。每条生成核心/细节/价值/原文。不足六条有据资讯时记录原因，不编造、不拿重复凑数。
> 4. 将完整简报写入 <NEWS_DIR>/AI新闻推送_<date>.md，并在项目当日 run 中保存输入快照。最终微信卡片正文以“# AI 新闻推送 · <date>”开头，只包含完整新闻内容；过程日志与故障状态写报告。正文目标 1500—3500 字符。
> 5. 从同一事实源生成短显示标题、至多两条关键结果、完整口播句和语义章节标题。保留显示专名，TTS 读法仅在合成边界转换。固定 edge 云希、语速 +30%；以真实合成与最终成片时长校验 50—60 秒，超时改写，不能字符硬截断或添加空尾。
> 6. 每条使用相关实拍照片，禁止文字卡、海报、无关头像；图库示意图显式标注。检查全部新闻句中的画面、KTV 黄白高亮、换行和遮挡。TTS 失败、素材缺失或发布前质量检查未通过时，保存 BLOCKED，停止发布。
> 7. 将最终 MP4、稿件、时间轴、章节、发布文案、素材信息和实测报告归档到项目 out/<date>/。发布封面由外部 video-upload 的大字模板生成并检查；采用既有署名与合集，不传 --cover-* 参数绕过重绘。
> 8. 只有最终视频哈希对应 READY 时，才由外部发布技能向抖音、B站、视频号发布。执行前先查同日期、同平台回执；已成功的不再发。结果不明确先核查平台，不把网络超时当成未发布。单平台失效不重复发布其他平台；遵守既有抖音重试/冷却上限。
> 9. 按日期更新 handoff 与平台回执，主视频记录绝对路径，区分生成、质量通过、提交发布与平台审核状态。保持 handoff≤24 KiB，历史证据引用归档文档。维护最新执行摘要，不输出密钥或 cookie。

当前提示词中的 Bash/PowerShell 命令应与实际执行器分开维护。已有 `python.exe` 在本次证据提取时确实可用，但这是现状而非推荐的新装位置；不为优化方案搬动共享工具链。实施时检测权威 F 盘运行时/缓存，若尚未具备则沿用已验证解释器并记录，不擅自升级或安装。

## 6. 分阶段原子任务与验收

估时按一名熟悉项目的开发者计算，是规划范围而非承诺。没有把每个任务强制限定为几十分钟；涉及显示字幕映射的工作必须先冻结契约并取得规格确认。各任务默认严格 TDD：先运行有效行为失败测试，再最小实现，再回归；文档修订使用一致性检查，不为 Markdown 本身造测试。

| 任务 | 依赖 | 预计文件与范围 | 验收/验证 | 估时 |
|---|---|---|---|---|
| T0 文档和运行配置收口 | 无 | `SKILL.md`、`USAGE.md`、`references/pipeline-contract.md`、定时提示词；如需配置单独成一小任务 | 文档不再声称脚本未恢复；E/G 路径一致；封面唯一职责明确；实际 `--help` 参数匹配；不改变 TTS 默认 | 1—2 h |
| T1 最终成片报告 | T0 | `finalize.py`、`render.py`、`run_all.py`＋报告测试 | 测最终文件时长/音轨/宽高/fps/哈希；自定义 out 正确；`--only render` 后也可完整收尾；缺少必要物料不可 READY；不覆盖既有平台回执 | 3—5 h |
| T2 正式质量硬门 | T1 | `validate_output.py`、契约、质量样本/测试 | 缺失真实图片文件、静音失败、日期/文本/音频指纹不符、坏相对字时标均失败；缺图海报不能进入正式成片；普通排版建议不一刀切阻断 | 3—5 h |
| T3 解析重跑幂等 | T0 | `parse_news.py`、`run_all.py`、去重状态测试 | 同日同输入连续两次得到同组条目；preview 不修改 seen；第二次失败不损坏前一次成功状态；跨日已用条目仍能去重 | 2—4 h |
| T4 TTS 缓存完整性 | T2 | `gen_tts.py`、缓存测试 | 同文本同配置复用；改字、音色或语速必失效；静音失败重试不能伪装 word/even 成功；只重生成失效句，不靠每次 force 全量重来 | 3—5 h |
| T5 时间基准与片尾 | T2 | `gen_tts.py`、`NewsVideo.tsx`、`videoConfig.ts`、小 fixture | 点击声/首字起点映射误差≤1 帧；最后实际视频帧仍有收尾画面，缓冲内无纯背景；现有字幕相对时间不变量保持 | 2—4 h |
| T6 可控混音与并发 | T1、T2 | `common.py`、`render.py`、`check_deps.py`、音频测试；若纳管 NumPy 分离子任务 | 真实微型链路预检；不支持的组合发布前失败；最终音频报告含 LUFS/TP；混音前后视频帧数不变、AV 结束偏差≤1帧目标；并发1基准通过 | 3—5 h |
| T7 显示稿/朗读稿分层 | T3、T4、T5；先确认字段契约 | 第一步 parser/fetch/稿件导出；第二步 gen_tts/术语映射；每步≤约5个文件 | 形成可审阅完整稿；fetch 不重写稿；显示专名正确；章节无半截单词；旧 narration 有明确适配/拒绝路径 | 4—8 h |
| T8 版式和选图 | T7 | 先 `NewsItem.tsx`/`Subtitle.tsx` 与视觉样本；再 `fetch_news.py`/图片回归集，分两切片 | 七条均照片且相关、来源非空；手机预览能读；正文字幕不相交；最长术语也不超两行字幕；三平台遮罩内无遮挡；逐条看句中帧 | 4—8 h |
| T9 运行隔离与发布回执 | T1、T3、T4 | 先日期/run 路径与素材快照，再主流程与外部发布交接协议；分切片实施 | 新 run 抓图失败不清旧 run 图片；每个平台成功回执关联最终视频 hash；超时先核查；同日补发仅缺失平台；凭证失效写待人工恢复 | 4—8 h |
| T10 样片对比与运营记录 | T5—T9 | `docs/testing/`、当日独立候选输出目录、运营记录 | 固定同一新闻分别出基线/优化样片；质量门全通过、人工听审与画面审阅；选择一个正式版，不将两版自动重复发布；收集同口径48h数据 | 制作2—3 h＋观察周期 |

**建议首轮实施范围：T0—T6。** 它们解决最容易反复出事故、且可直接验证的问题；T7—T8 是第二轮主观观感提升重点。两轮合计约 3—6 个工作日，受字幕映射、素材可用性与运行环境影响；不沿用旧方案“全部一两小时”的乐观估算。

阶段检查点：

- **C1（T0—T4）**：重复执行不需要删 seen 当日键；缓存不读错稿；关键失败真实拦截；最终 run report 与 MP4 一致。此时还不能称新视觉方案完成。
- **C2（T5—T8）**：相同新闻输入产生 50—60 秒候选片，前 3 秒有完整具体事件，末尾无纯背景；7/7配图通过既有照片要求；字幕、主标题、正文可读；手机外放与耳机听审均记录。
- **C3（T9—T10）**：故障注入不损坏前一次产物；无 READY 或 hash 不符时发布器拒绝；单平台失败与其他平台成功可分开恢复。真实平台提交需要沿用实际授权与当前凭据状态，本次没有执行。

### 必备回归用例

1. 同日相同文件 parse 两次、preview 一次；输入文件和状态账本原始指纹留存，不能为了测试删除正式去重状态。
2. narration 与 timeline 日期相同但文本不同、相同长度不同文字、不同音色/语速缓存，均需正确失效或阻断。
3. `images` 数组存在但文件不存在、图片损坏、文字卡、缺图片，均不能正式发布。
4. clause start≥end、相对字时标越界/逆序、静音 fallback、缺失时间轴，逐项取得行为 Red 再 Green。
5. 标准 BGM、空 BGM 目录、FFmpeg 有 loudnorm 但没有 sidechaincompress，分别有可预期状态；不把“能找到 exe”当混音可用。
6. 当前 10-12 三行字幕、超长英文专名、10-14 342字符正文、末尾缓冲，在真实字体与1080×1920渲染中验证。
7. 渲染返回成功但最终 MP4 缺音轨/时长不符；混音失败或返工改变 hash；报告不能继续显示旧 READY。
8. 发布返回超时、某平台成功后进程崩溃、补发时其他平台已有成功回执；不发生盲目重传。

### 风险、边界与回滚

- **Always**：保留云希与相对字时标契约；照片硬要求；最终文件实测；本地稿件和日志不含凭据；保护当前未提交改动。审阅时工作树已有源代码、技能和资源改动，不能用 reset/checkout 覆盖。
- **Ask first**：确认完整口播/字幕字段契约和样片风格后进入重要实现；更换音色、扩大素材类型、安装依赖或调整共享运行时、修改已上线定时任务、处置/重发已发布版本、commit/push 需要相应授权。
- **Never**：静音或海报兜底冒充合格；清空共享 work 来恢复运行；拿过期/未核实新闻凑数；假设超时意味着没发布；把所有平台重新发一次当补发。
- 每个切片独立验证并保留前版配置/输入，不自动提交。验证失败回到可运行切片，保留失败报告；新版本数据使用显式 schema 版本，避免旧数据静默误读。
- 不做全量历史视频重渲染，不修改线上历史作品；旧手工脚本保留为历史证据，只有正式纳管的代码替代后才考虑清理。

### 运营效果如何判断

当前没有播放量、前几秒留存、平均观看时长、完播率或收藏率基线，因此不给“提升30%”式承诺。至少记录每期平台、发布时间、视频版本、长度、主题、曝光/播放、平均观看秒数、可获得的留存/完播/收藏指标；口径以平台实际提供为准。先收集约7期基线，再观察约7期优化版，记录主题热度与发布时间差异。这是观察性对比，不等同随机 A/B 因果实验。不要把同一新闻的两版连续发到同一账号测试，避免重复内容与相互干扰。

## 7. 外部依据与旧方案处理

### 7.1 官方资料与三个主要标杆

以下资料于2026-10-14访问，采用一手文档。在线Remotion资料可能含4.0.520之后新增的选项或示例；本项目实际版本已核验为4.0.520，实施前仍要核对本地CLI帮助或对应版本源码，不直接照搬最新参数。

1. **Remotion渲染器：输入与资源可控。** [renderMedia](https://www.remotion.dev/docs/renderer/render-media)、[concurrency](https://www.remotion.dev/docs/options/concurrency)。官方允许显式控制并发数；借鉴点是按机器测量配置资源，不是从核心数推断安全并发。本项目保留Remotion，先把命令实际输入和前端读取输入连成一条证据链。
2. **Remotion内存与Sequence语义。** [render CLI](https://www.remotion.dev/docs/cli/render)、[parallel encoding](https://www.remotion.dev/docs/parallel-encoding)、[useVideoConfig](https://www.remotion.dev/docs/use-video-config)。禁止并行编码可以减少浏览器和编码器同时占用的内存，但可能变慢；是否采用需本地验证。官方明确，Sequence内的`durationInFrames`为该Sequence在局部帧空间的终点；当前无变速/裁切时是局部时长，**NewsItem/ImageViewer使用此值不能被误报为用了整片时长**。
3. **Remotion输入约束。** [schemas](https://www.remotion.dev/docs/schemas)。schema可以给props添加校验与约束。借鉴其边界校验机制，继续用现有Python校验器实现首期关键不变量；不为本次方案新增Zod依赖。
4. **FFmpeg：把“听起来正常”拆成可测指标。** [loudnorm](https://ffmpeg.org/ffmpeg-filters.html#loudnorm)、[sidechaincompress](https://ffmpeg.org/ffmpeg-filters.html#sidechaincompress)、[ebur128](https://ffmpeg.org/ffmpeg-filters.html#ebur128)。`loudnorm`支持综合响度、响度范围与真峰值目标，以及单/双遍模式；侧链压缩用第二路信号控制第一路；`ebur128`区分瞬时、短时、综合响度等。本次已从官方正文提取相关段落并保存到[官方摘录](evidence/2026-10-14/ffmpeg-official-excerpts.json)。借鉴点是测原片、测实际构建、必要时双遍处理，不能因为完整文档有某滤镜就宣称本地裁剪构建能用。-14 LUFS是项目建议目标，不是从这份标准推出的平台统一要求。
5. **Airflow：可重复任务与明确分区。** [3.0.5最佳实践](https://airflow.apache.org/docs/apache-airflow/3.0.5/best-practices.html)；亦核对了[当前stable文档](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html)。官方要求把任务视为事务、避免不完整结果、重跑产生相同结果，并读写指定分区而非动态latest。这里直接借鉴日期输入快照、临时文件成功后替换、状态延迟提交，不引入Airflow调度服务，其分布式远程存储建议也不应直接照搬到本机短视频项目。
6. **TikTok广告安全区：只能借鉴检查方式。** [Auction In-Feed Ads](https://ads.tiktok.com/help/article/tiktok-auction-in-feed-ads?lang=en)（页面标注2026年6月更新）。安全区受画幅、caption长度和附加格式影响，预览与真机可能不同。这是TikTok广告资料，不能当作抖音/B站/视频号自然视频的统一像素规范；本方案的区域数值须用真实播放UI复验。

本次没有新增第三方依赖或移植外部源码；许可条件不作未经核实的放宽判断。Remotion沿用项目现有版本及使用条件；未来更换FFmpeg构建或引入模型/库时，另核构建许可、分发条件和商业使用范围。没有用论文中的不匹配benchmark替代本项目的三期成片证据。
